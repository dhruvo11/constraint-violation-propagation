How CVP works

CVP attributes document forgery: it says whether a document was edited and which field was changed, even when an AI-style edit leaves almost no trace in the pixels.

Generative inpainting removes the pixel traces that forensic detectors look for, but it does not know the document's arithmetic. CVP uses the rules a forged value breaks to shrink the list of suspect fields, then uses even weak visual evidence to pick the edited field within it.

A worked example

One blended edit on a transcript

Statement of marks (seed 2)
Machine Learning69
Database Systems59
Data Structures77
Computer Networks32
Linear Algebra91
Total311

The forger changed mark 3 from 60 to 77 with an inpainting-like edit that looks clean.

The marks now add up to 328, but the printed total is 311: rule c1 (sum of marks = Total) breaks. Nothing else does.

Any of the five marks could have caused exactly this: each enters c1 the same way. They form one class, so the rules narrow 10 fields to 5 suspects.

The heatmap is faint, but among those five it is highest on mark 3, so CVP blames mark 3. That's correct.

Neither branch could do it alone: the rules cannot say which mark, and the heat is too weak to stand out across the whole page.

The theory in code

Proposition 1: fields the rules cannot tell apart

Two fields are equivalent when every rule that reads one also reads the other and treats them the same way (as terms of a sum, or the factors of quantity × rate). An edit of either then breaks exactly the same rules, so no amount of rule-checking can separate them. This is the function, from cvp/core/schema.py:

def equivalent(a, b):
    shared = False
    for c in non_unary:                        # every rule with 2+ fields
        ina, inb = a in c.scope, b in c.scope
        if ina != inb:                        # one rule reads a but not b:
            return False                       #   the rules can tell them apart
        if ina:
            if not any(a in g and b in g for g in c.exchangeable):
                return False                   # read, but in different roles
            shared = True
    return shared

Each class then gets a signature: the rules any edit of it must break, and the ones it may break. signature_class(w) looks up the class whose signature matches the broken rules w, and consistent_fields(w) lists every field that could explain them. A document type only declares its fields and rules; all of this is derived automatically.

Data and training

Where the data and the models come from

Synthetic documents

Each document type generates its own pages, valid by construction, with every field's position and value known. That gives exact ground truth for every forgery, and no personal data. Per type: 2,000 training, 500 validation and 1,500 test documents.

Real documents

CORD v2: 1,000 real receipt photos from Indonesian shops (CC BY 4.0). Find it again! (ICDAR 2023): 988 scanned receipts, 163 forged by people with image editors.

Models we trained

The CRNN reader, the ResNet-18 U-Net (synthetic, then fine-tuned on real photos), and two small heads: a class model (MLP) and a detector (logistic regression).

Fair evaluation

Separate train, validation and test splits. The test's blended forgeries come from a generator no model saw. Design choices were made on validation data, never on the test set, and every alternative is reported.

Likely questions

If you're asked

What problem does this solve?

Image-editing and AI tools can change a number on a marksheet or a receipt and leave almost no trace in the pixels, so detectors that look only at pixels miss it. Documents, though, follow rules: totals, check digits, dates. CVP uses those rules as a second, independent source of evidence.

What is new compared with existing forgery detectors?

Most detectors only say "edited or not" from pixels. CVP says which field was edited, and it combines two kinds of evidence. Proposition 1 makes precise which fields the rules can never tell apart, so the visual branch is needed only to choose within that small set, and even weak visual evidence is enough there.

Why use synthetic documents?

They give exact ground truth (which field changed, which pixels), all four forgery kinds, and no personal data. Phase 2 then checks the method on real data: 1,000 real receipt photos and 988 receipts forged by real people.

How does it pick the field when several fit the broken rules?

The rules nominate a class of suspects, such as "one of the five marks". The heatmap scores each suspect's box, and the hottest suspect is blamed. When no rule breaks, every field is a suspect and the heatmap decides alone.

Which models and tools does it use?

Python with PyTorch. We trained a CRNN reader for the templates and a ResNet-18 U-Net for the heatmap. docTR, a free open-source OCR, reads real photos. scikit-learn fits the small decision heads, and Gradio serves the web app. Everything is free and runs locally.

How do you know the results are fair?

Training, validation and test documents are separate. The blended forgeries in the test set come from a generator the models never saw. The design of the decision head was chosen on validation data from an older generator, never on the test set, and every alternative is reported as an ablation.

Can it handle a new kind of document?

Yes. A new type is one module that declares its fields and rules, a page template and a forger. The classes, signatures and suspect sets are derived automatically. Real receipts go further: each one gets its own rule graph built from the values it prints.

How fast is it?

About a second per synthetic document and about two seconds per real photo on this laptop. Training everything from scratch takes a few hours.

Limits

What it cannot do yet

Complete forgeries (T4). When every dependent value is repaired and the edits are blended, no rule breaks and little heat remains: caught only some of the time.

OCR noise on real photos. Misread digits break rules on genuine receipts: about 11% of genuine real receipts are flagged.

Copy-paste forgeries. Real forgers often copied digits from the same receipt, which our visual branch cannot see; that needs a copy-move detector.

Unconstrained fields. A name that no rule reads rests on the visual branch alone.
