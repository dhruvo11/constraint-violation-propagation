## 4.3 DOCUMENT TEMPLATES AND RENDERING

Each document type is a Python class that declares its fields and rules, draws a template and knows how to forge itself. The templates are drawn with Pillow from scratch, with fonts, lines, logos made of simple shapes, watermarks and tables (Figure 4.1). All issuers are fictional: the transcript and ID card come from an "Institute of Advanced Technology", the certificate from a "Skillnest Academy", and the passport follows the layout of Utopia, the specimen country used by ICAO Doc 9303.

!figure report/final_report/figures/doctypes.png | 5.6 | Figure 4.1: One Genuine Document of Each of the Six Synthetic Types

Values are generated so that every document is consistent: marks are drawn from a normal distribution around 66 and clipped to the valid range, invoices get random line items, tax regimes and place of supply, receipts get random baskets and payments, passports get valid check digits, and so on. The page offset varies by up to 8 pixels and each field by up to 2 pixels, the paper tint and ink tone vary per document, and the transcript and invoice carry a faint watermark. An acquisition model then adds Gaussian blur, sensor noise and a first JPEG compression (quality 82 to 95). Every document, genuine or forged, is finally saved once more as JPEG (quality 75 to 92), so that a second compression on its own gives nothing away.

## 4.4 FORGERY GENERATION

The forger of each type implements three methods: choosing a violating value for a field (for T1 and T2), making a coherent edit that also updates every dependent field (for T3 and T4), and drawing random values. The renderers in `cvp/core/tamper.py` then draw the edit:

- **Crude rendering (T1, T3):** the field is filled with the median background colour and the new value is typed in a different font (bold, serif, monospace or another size). This destroys the local noise, texture and watermark.
- **Blended rendering, generator G2 (T2, T4):** the page is rendered again with the new value in the document's own font and layout, passed through the acquisition model with weaker noise (scaled by 0.5 to 0.85) and extra blur (0.3 to 0.7), and alpha-blended into the original with a feathered mask. This imitates the smooth, slightly over-cleaned look of diffusion inpainting.
- **Older blended generator G1 (training only):** stronger smoothing (noise scaled by 0.15 to 0.45, extra blur 0.9 to 1.5) and a hard-edged mask.

The forger records which fields were edited, their old and new values and the edited pixel regions, which gives exact ground truth for every test.

## 4.5 OCR: TEMPLATE REGISTRATION AND CRNN READER

Because each document type has a known layout, the reader first registers the page by finding a horizontal header rule, which fixes the global offset, and then crops each field from its slot. Each crop is resized and read by a CRNN: convolutional blocks, a bidirectional LSTM and a CTC output over a 39-symbol alphabet. Long lines, such as the passport's machine-readable zone and amounts written in words, are read from crops four times wider. Decoding is restricted to the characters a slot can contain, and the field box is the tight box around the ink in the slot.

A single recogniser serves all six types. It was trained for 4,000 steps on 126,000 normal and 21,000 wide crops cut from synthetic documents whose values were drawn beyond the valid range on purpose. This matters: an OCR that has only seen valid documents learns what values are likely and may quietly "correct" a forged value into a plausible one, which would hide the very violation we want to detect. The crops also pass through every forgery renderer, and a third of them are degraded by JPEG compression or resampling. ## 4.6 VISUAL BRANCH: RESNET-18 U-NET WITH ELA

The visual branch is a U-Net with a ResNet-18 encoder initialised from ImageNet and a full-resolution skip connection, so the heatmap has the same size as the input page. Error Level Analysis is computed as the difference between the image and a quality-90 re-encoding of it and added as a fourth input channel; its first-layer filters are initialised as the mean of the RGB filters. We chose a small backbone on purpose, since our training documents are rendered and a larger encoder would more easily overfit to rendering details.

Training uses 256 × 256 patches cut on the 16-pixel JPEG block grid, so that ELA computed on a patch is exactly the same as ELA computed on the whole page. The loss is binary cross-entropy plus Dice against the edit masks. The network is trained for 3,000 steps with batch size 8, the AdamW optimiser (weight decay 0.0001) and a one-cycle learning-rate schedule with a peak of 0.001, which takes under 80 minutes on the laptop. One network is trained for all six types together on genuine, T1, T3 and G1-blended documents. Two more versions were trained for the experiments in Section 5.5: one on crude edits only (zero-shot) and one that also saw G2 (oracle). At test time the network runs on the whole page at once.

## 4.7 CONSTRAINT EVALUATION, CLASS POSTERIOR AND HEADS

The rules of each type are written as small Python objects with a scope, a check function and a residual. `cvp/core/schema.py` derives everything else automatically from these declarations: the equivalence classes of Proposition 1, the necessary and possible signatures of each class, the consistent set for an observed pattern and the reduction factor. Adding a new document type therefore only requires declaring its fields and rules; the theory is applied to it without further code.

The class-posterior network g_φ is a scikit-learn MLP with two hidden layers of 64 units, trained on the training-split features (violations, residuals, parse failures and OCR confidences). Its accuracy at predicting the edited class ranges from 87.1% (certificate) to 99.9% (transcript). The attribution head has four non-negative weights, fitted with L-BFGS on validation features, and the visual detection score is a logistic regression on four pooled heat statistics. All thresholds are chosen on validation data, never on the test set. Six head designs were compared on the separate G1 validation set before any test result was seen, as described in Chapter 5.

## 4.8 REAL RECEIPT PIPELINE

Real receipts needed their own pipeline because every shop prints different fields and follows its own conventions:

- **Reading:** CORD gives a box for every labelled word, and we use these boxes like a template. docTR's CRNN recogniser reads each value inside its box, padded by three pixels. For Find it again!, which has no positions, docTR's text detector finds the words, the words are grouped into printed rows, and each keyword (TOTAL, CASH, CHANGE, ROUNDING and so on) is paired with the rightmost amount on its row.
- **Rules:** six receipt rules (line, sum, total, change, tender and count) allow for prices that already include tax, service charges, add-on items, item discounts and split payments. Each receipt gets its own constraint graph over the fields it actually prints, and the same theory applies to it unchanged.
- **Forging with ground truth:** the forger repaints values directly on the photographs. T1 paints over a value in the paper colour and retypes it; T2 removes the digits by inpainting and draws new ones in the receipt's own ink colour, size and softness; T3 and T4 change an item price and update every dependent value. New values keep the digit count and number style of the old ones, and every output is saved again as JPEG quality 90.
- **Visual branch:** each photo is resized so that its longer side is at most 1,600 pixels. The synthetic model is used as it is (zero-shot) or fine-tuned for 3,000 steps on 3,859 training images made from the 800 training receipts, either with crude edits only or with every category.
- **Decision:** because each receipt has its own schema, CVP uses the deterministic signature lookup: the broken rules give the consistent set and the heatmap picks a field within it. The detection threshold maximises Youden's J on the 489 validation images.

## 4.9 THE WEB APPLICATION

The CVP web app (`webapp/`) is what a user, or an evaluator, actually sees. A small FastAPI server runs CVP on the laptop and answers the page's requests with plain data; the page itself is hand-written HTML, CSS and JavaScript with no build step, so it works offline. Nothing that is uploaded leaves the computer. When the server starts, the models load in the background and the examples are computed in advance, so that clicking one is instant during a demonstration. The double-click launcher `Start CVP.command` starts it at http://127.0.0.1:7860.

The app has four views:

- **Analyse:** run a ready-made example, forge a document on request (any of the six types or a real CORD receipt photo, any kind of forgery, any field), or upload an image.
- **Guided tour:** seven steps for a demonstration, each with what to notice: a genuine mark sheet, an obvious edit, a smooth AI-style edit, a case the rules cannot decide, a real receipt photo, a real GPT-Image-2 forgery and, last, an edit that keeps every rule, which shows the limit of the method (Figure 4.2).
- **How it works:** the method in five steps, the architecture figure and the illustrated explainer.
- **Results:** the headline numbers of the evaluation, read from the saved results, with the figures of Chapter 5.

Every result is shown the same way. A verdict card gives the decision (tampered, genuine, a warning, or cannot verify), the field that was edited and one sentence of reasons. Five numbered steps then explain the decision in plain English: what was read, which rules were checked and which broke, which fields the broken rules fit (with a pointer to Proposition 1 when several fit equally), how much edit evidence the pixels show on each suspect, and the decision. Every rule is listed with its actual numbers, for example "82,000 + 61,000 + 51,000 = 194,000; the subtotal says 109,293". The document is shown with layers that can be switched on and off: the heatmap, the fields the broken rules fit, the blamed field and, when the forgery is ours or from AIForge-Doc, the field that was really edited, with an answer key that says whether CVP was right. Hovering over a field shows what was read there and its heat.

**Any receipt photo (experimental).** Uploaded receipts and bills have no layout labels, so `cvp/real/upload.py` reads them end to end: docTR finds and reads every word, the words are grouped into printed rows, and each row is classified as an item (a name and a price above the bill's summary) or as a bill line (subtotal, tax, service charge, discount, rounding, total, cash, other payment, change, item count) by its keywords. It handles Indian GST bills (CGST and SGST lines are added together, amounts such as 1,23,456.00 are read whole, quantity × rate lines are checked) as well as Indonesian and Malaysian receipts, corrects near-misses of the keywords that the OCR produces ("SUB_TSTAL", "Servi Charge"), and treats an unnamed amount between the subtotal and the total as a charge. The values then fill the same receipt structure as a CORD receipt, so the receipt gets its own constraint graph and the theory applies unchanged. Because item lines are much harder to read than the bill's own lines, only the bill-level rules (subtotal + tax = total, cash − total = change, and the payment covers the total) raise an alarm; the item-level rules only raise a warning, and the heatmap only ranks the suspects. If the OCR misreads a value, the user can type what the photo shows and re-check the rules (Figure 4.3). On the 100 CORD test photos read without their labels, it raises a false alarm on 6% of genuine receipts, close to the 6.7% of genuine receipts that break a rule even when every value is read correctly, and warns on another 12%; it alarms or warns on 54% of our smooth single-field edits of the same photos (`scripts/real_upload_check.py`).

## 4.10 TESTING AND REPRODUCIBILITY

The project includes 367 automated tests written with pytest. They check the theory (equivalence classes, signatures, consistent sets and the reduction factor, including a property test of Proposition 1), every rule of every document type, rendering and forgery generation, the scoring code, the trained models and the real-data pipeline. Results are covered in Section 5.1.

Every result can be rebuilt from scratch. `scripts/reproduce.sh` generates the synthetic data, trains the OCR and visual networks, extracts features, fits the heads, evaluates every method and draws every table and figure, which takes a few hours on the laptop. `scripts/reproduce_real.sh` does the same for the real-data experiments from the public datasets. A setup script creates the Python environment, and a double-click launcher starts the application. The large generated files (datasets, features and model weights) are not stored in Git, while the small outputs (results, tables, figures and the paper) are.
